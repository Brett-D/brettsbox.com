--- title: "Basalt vs cuVSLAM, round one: CPU or GPU?" slug: basalt-vs-cuvslam date: 2026-11-14 tags: roomba, vslam, gpu summary: The robot can work out how it's moving with Basalt on the CPU or NVIDIA cuVSLAM on the GPU. The GPU holds still better; Basalt stays on track better once it moves. Here's the scorecard so far. ---

The robot now has two ways to work out how it's moving. Basalt runs on the Jetson's CPU and NVIDIA cuVSLAM runs on its GPU. Both watch the same stereo camera and IMU, and one launch argument picks which one is in charge. That makes for a fair fight: I can record a run once and replay exactly the same camera frames through each.

The side-by-side maps are still to come, but the early numbers already tell an interesting story: the GPU is not simply better.

Standing still: the GPU wins

The simplest honest test is to park the robot and ask it how far it has moved. The right answer is zero. Over a minute, the CPU pipeline thought the robot had crept 0.9 cm and the GPU pipeline 0.3 cm. Fuse the calibrated wheels into the GPU pipeline's filter and it drops to 0.07 cm, as I found in the last post.

On the move: Basalt wins

Parking is the easy case. For the hard one, I carried the camera around the house, recorded everything it saw, and replayed the recording through both.

A jump is when the odometry suddenly decides the camera has teleported more than half a metre. The watchdog catches those so they never reach the map, but each one is a moment when the robot doesn't really know where it is. Basalt had none. cuVSLAM had 16, and its idea of the camera's height drifted about ten times as far as Basalt's. On the robot, cuVSLAM is told to stay in the floor plane, so height drift matters less there, but it's a good sign of how well each one is really tracking.

It started at 544

The first replay through cuVSLAM was a disaster: 544 jumps and 260 km of imagined travel in four minutes. Its default IMU settings are tuned for Intel RealSense cameras and trusted this camera's IMU far too much, so ordinary sensor noise looked like real motion. Telling it the IMU is ten times noisier brought that down to 16 jumps, and the number of times the watchdog caught vision disagreeing with the gyro fell from 157 to 31.

Why the map cares

Drift is what loop closure has to clean up. When RTAB-Map recognises a place it has seen before, it checks the match by counting the features both views share, then pulls the map straight.

With cuVSLAM, the corrections were big enough that I had to loosen that check to 15 matching features and tell RTAB-Map the odometry was less certain. Otherwise it rejected real loop closures, including one that needed a 7° correction. With Basalt, that loose check became a liability: similar-looking doors matched the wrong place and warped the map. Raising it to 25 gave a clean map on the same walk. Better odometry lets the map be pickier, and being picky is what keeps it straight.

So which one drives?

For now, Basalt. Staying on track while moving matters more than holding still, so the CPU pipeline is still the robot's default. The GPU pipeline is staying too: it takes the load off the CPU, and with the wheels fused in, it's the steadiest when parked. One launch argument switches between them.

Round two: maps

Numbers are nice; maps you can overlay are better. The next test replays one recorded drive through both pipelines, each building its own map from scratch, with the robot's drivers switched off so nothing can move. It counts tracking losses and loop closures, measures the map's area, and checks how far from the start each one thinks the robot finished. If the drive ends where it began, the right answer is zero. It also records how hard each one works the CPU and GPU.
