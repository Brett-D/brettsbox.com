The CPU pipeline from the last navigation post works, but it keeps the Jetson's six CPU cores busy while its GPU mostly sits there. This week I moved the heavy lifting onto the GPU and rebuilt how the robot works out where it is.

The new stack

  • NVIDIA cuVSLAM replaces Basalt for visual odometry. Same job (estimate motion from the stereo cameras and IMU), but on the GPU.
  • robot_localization runs an extended Kalman filter (EKF) that fuses every motion source into one best estimate.
  • nvblox builds a 3D model of nearby obstacles from the depth camera, on the GPU, and turns it into a costmap for Nav2.

Fusing wheels, gyro and vision

An EKF is only as good as what you tell it about each sensor, so I calibrated each input before letting it in:

  • Wheel speed, with measured correction factors: forward distance × 0.952 and rotation × 0.71. That second number is the carpet scrub from last time, now measured and corrected.
  • The camera's gyro, using noise figures from a three-hour stationary IMU recording and a measured static gyro bias, so the filter knows exactly how much to trust it.
  • Visual odometry, fused differentially. The filter uses the change in the VIO pose between updates rather than the pose itself. If cuVSLAM loses tracking and resets, it can't teleport the robot across the room.

Results: standing still

The simplest honest test is to park the robot and watch how far it thinks it has moved:

PipelineTestApparent drift
CPU (Basalt)Parked, 60 s0.9 cm
GPU (cuVSLAM)Parked, 60 s0.3 cm
GPU + wheels in the EKFParked, 30 s0.07 cm, 0.03°

Standing still is the easy case, of course. The real test is driving, which is next.

What went wrong (and got fixed)

The costmap that walled the robot in

I first added nvblox's obstacles to both of Nav2's costmaps. In the global costmap, which lives in the map frame, its marks never cleared, and every time RTAB-Map corrected the map they smeared sideways. After a few minutes the robot was surrounded by phantom walls. Now nvblox only feeds the local costmap, a small window that rolls along with the robot and is rebuilt constantly.

The node that froze mid-drive

Halfway through a test drive, my floor-obstacle node stopped publishing. The cause was a race between a ROS 2 TF listener's background thread and my own code. The good news: the collision monitor noticed the missing data and stopped the robot, exactly as designed. The race is fixed, and I trust that safety layer a lot more now.

A bump reflex

When the bumper does trigger, the robot now has a reflex: back up about 8 cm and turn away, before the planner tries again. It's a small thing that makes it look a lot less stuck.

Faster storage

Recording stereo images, depth and every sensor topic eats disk bandwidth. I swapped in a faster 256 GB NVMe drive, which manages about 1.8 GB/s on the Jetson's PCIe Gen3 x4 slot.

The code: vslam.launch.py starts cuVSLAM and the EKF; their settings, and nvblox's, are in ekf_robot.yaml and nvblox_robot.yaml.
